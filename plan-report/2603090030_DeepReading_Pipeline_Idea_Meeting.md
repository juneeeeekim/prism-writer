## 0. 회의 개요

### 회의 제목

**"검색 결과 딥 리딩(Deep Reading) 파이프라인 설계 — 스니펫에서 본문 추출·요약·검증까지"**

### 배경

현재 PrismLM의 웹 검색(Brave Search + Tavily)은 검색 엔진이 반환하는 **스니펫(description, 2~3줄)**만 활용하고 있습니다.
실제 페이지의 본문을 읽지 않기 때문에, 웹 검색 결과의 정보 깊이가 제한적입니다.

```
현재 흐름 (AS-IS):
사용자 질문 → Brave/Tavily 검색 → 스니펫(2~3줄)만 수집 → LLM에 전달

목표 흐름 (TO-BE):
사용자 질문 → Brave/Tavily 검색 → 상위 URL 선별 → 페이지 본문 크롤링 → 핵심 추출·요약 → LLM에 전달
```

### 회의 목적

- 웹 검색 결과의 **실제 페이지를 크롤링**하여 본문을 추출하는 파이프라인 설계
- 비용, 지연시간, 신뢰도 검증을 고려한 **실현 가능한 아키텍처** 도출
- 기존 PrismLM 시스템(RAG, Self-RAG, Citation Gate)과의 **통합 전략** 수립

## 2. 현재 시스템 분석 (AS-IS)

### 2.1 현재 웹 검색 데이터 흐름

```
POST /api/chat (사용자가 "웹검색" 키워드 포함 시)
├── performWebSearch(query)
│   ├── Brave Search API → BraveWebResult[]
│   │   └── title, url, description(스니펫), age
│   └── Tavily API (학술 키워드 시) → TavilySearchResult[]
│       └── title, url, content(요약), score
├── formatWebContext(webResults)
│   └── 스니펫을 "[1] 제목 (URL)\n내용" 형태로 포매팅
├── buildSystemPrompt({ webContext })
│   └── 프롬프트 하단에 "외부 웹 검색 결과" 섹션 삽입
└── LLM 스트리밍 응답
```

### 2.2 현재 한계점

| 항목            | 현재 상태                    | 문제점                 |
| --------------- | ---------------------------- | ---------------------- |
| **정보 깊이**   | 스니펫 2~3줄 (50~150자)      | 맥락 부족, 피상적 답변 |
| **본문 접근**   | ❌ URL만 보유, 페이지 미방문 | 핵심 내용 누락         |
| **팩트 검증**   | 스니펫 수준에서만 가능       | 원문 대조 불가         |
| **인용 정확도** | 스니펫 기반 추론             | 원문과 괴리 가능       |

### 2.3 활용 가능한 기존 자산

| 자산                  | 파일 위치                                  | Deep Reading에서 재활용 |
| --------------------- | ------------------------------------------ | ----------------------- |

| 결과 요약기           | `lib/research/resultSummarizer.ts`         | 본문 요약 로직 확장     |

| Progressive Streaming | `api/chat/route.ts`                        | 상태 메시지 확장        |

#### 1-2. 추천 전략: 2-Tier 크롤링

> PrismLM이 Vercel에 배포되어 있다는 점이 핵심 제약입니다. Puppeteer는 서버리스에서 사실상 불가능합니다.
> **Jina Reader API를 1차 크롤러로, @mozilla/readability를 폴백으로** 쓰는 2-Tier 구조를 추천합니다.

```
크롤링 요청
    │
    ├── 1차: Jina Reader API (r.jina.ai/{url})
    │   └── 성공 → 마크다운 본문 반환
    │   └── 실패/타임아웃 → 2차로 폴백
    │
    └── 2차: fetch + @mozilla/readability (폴백)
        └── HTML 직접 fetch → Readability로 본문 추출
        └── JS 렌더링 필요 페이지는 스킵 (graceful skip)
```

### 안건 2: 본문 추출 품질 — HTML → 클린 텍스트 전환 전략

**발언자: 윤서연 (정보 추출 & NLP 전문가)**

> 안녕하세요, 윤서연입니다. 비정형 텍스트에서 핵심 정보를 추출하는 NLP 파이프라인을 전문으로 합니다.

#### 2-1. 본문 추출 파이프라인 (4단계)

```
Raw HTML/Markdown
    │
    ├── Stage 1: 노이즈 제거 (Boilerplate Removal)
    │   └── 네비게이션, 광고, 사이드바, 푸터, 쿠키 배너 제거
    │   └── Jina Reader 사용 시 이 단계 자동 처리
    │
    ├── Stage 2: 본문 정규화 (Normalization)
    │   └── 연속 줄바꿈 → 단일 줄바꿈
    │   └── 불필요한 마크다운 문법 정리 (중첩 링크 등)
    │   └── 이미지 alt 텍스트만 보존, 나머지 미디어 태그 제거
    │
    ├── Stage 3: 길이 제한 (Truncation)
    │   └── 최대 5,000자로 제한 (약 1,500~2,000 토큰)
    │   └── 앞부분 우선 (뉴스/블로그 = 역피라미드 구조)
    │   └── 학술 논문 = Abstract + Conclusion 우선 추출
    │
    └── Stage 4: 구조화 (Structuring)
        └── 제목, 작성일, 저자 메타데이터 추출
        └── 본문을 문단 단위로 분리
        └── 각 문단에 위치 태그 부여 (intro/body/conclusion)
```

#### 2-2. 페이지 유형별 추출 전략

| 페이지 유형       | 감지 방법                     | 추출 전략                 | 최대 길이 |
| ----------------- | ----------------------------- | ------------------------- | --------- |
| **뉴스/블로그**   | URL 패턴, `<article>` 태그    | 역피라미드: 첫 3문단 우선 | 3,000자   |
| **학술 논문**     | arxiv.org, pubmed, .edu       | Abstract + Conclusion     | 4,000자   |
| **기술 문서**     | docs., developer., API 키워드 | 목차 기반 관련 섹션 추출  | 5,000자   |
| **위키피디아**    | wikipedia.org                 | 첫 섹션 + infobox         | 3,000자   |
| **일반 웹페이지** | 기본값                        | 전체 본문 앞부분          | 3,000자   |

#### 2-3. 한국어 특수 처리

> PrismLM 사용자가 한국어 중심이므로, 한국어 웹 페이지의 특수성을 고려해야 합니다.

| 특수성                       | 대응                                                    |

### 안건 3: 토큰 예산 분배 — RAG 컨텍스트 vs 웹 본문 비율

**발언자: 박준혁 (LLM 컨텍스트 최적화 전문가)**

> 안녕하세요, 박준혁입니다. LLM의 컨텍스트 윈도우를 최적으로 활용하는 전략을 연구하고 있습니다.

#### 3-1. 현재 토큰 예산 분석

```
현재 PrismLM 프롬프트 구조 (예상 토큰):
┌─────────────────────────────────────────┬──────────┐
│ 시스템 프롬프트 (역할 + 규칙)            │ ~800 토큰 │
│ 사용자 선호도 (User Preferences)         │ ~200 토큰 │
│ 루브릭 템플릿 (평가 기준)                │ ~300 토큰 │
│ RAG 컨텍스트 (사용자 문서)               │ ~2,000 토큰 │
│ 웹 검색 스니펫 (현재, 5개)               │ ~500 토큰 │
│ 대화 히스토리                            │ ~1,000 토큰 │
├─────────────────────────────────────────┼──────────┤
│ 합계 (입력)                              │ ~4,800 토큰 │
│ 출력 예산 (maxOutputTokens)              │ 2,700 토큰 │
├─────────────────────────────────────────┼──────────┤
│ 총 사용량                                │ ~7,500 토큰 │
│ gemini-3-flash 컨텍스트 윈도우           │ 1,000,000 토큰 │
│ 여유 공간                                │ 충분 ✅ │
└─────────────────────────────────────────┴──────────┘
```

#### 3-2. Deep Reading 후 토큰 예산 재설계

> 크롤링 본문이 추가되면 웹 컨텍스트가 500 → 3,000~6,000 토큰으로 증가합니다.
> 하지만 Gemini 3 Flash의 1M 토큰 윈도우에서는 **전혀 문제가 되지 않습니다.**
> 오히려 **비용**이 핵심 관심사입니다.

```
Deep Reading 후 프롬프트 구조 (예상 토큰):
┌─────────────────────────────────────────┬──────────┐
│ 시스템 프롬프트 (역할 + 규칙)            │ ~800 토큰 │
│ 사용자 선호도 (User Preferences)         │ ~200 토큰 │
│ 루브릭 템플릿 (평가 기준)                │ ~300 토큰 │
│ RAG 컨텍스트 (사용자 문서)               │ ~2,000 토큰 │
│ ★ 웹 본문 (Deep Reading, 3페이지)        │ ~4,500 토큰 │
│ 대화 히스토리                            │ ~1,000 토큰 │
├─────────────────────────────────────────┼──────────┤
│ 합계 (입력)                              │ ~8,800 토큰 │
│ 출력 예산 (maxOutputTokens)              │ 2,700 토큰 │
├─────────────────────────────────────────┼──────────┤
│ 총 사용량                                │ ~11,500 토큰 │
│ 비용 증가율                              │ +53% (7,500 → 11,500) │
└─────────────────────────────────────────┴──────────┘
```

#### 3-3. 토큰 예산 분배 전략

| 전략                       | 설명                                                       | 추천       |
| -------------------------- | ---------------------------------------------------------- | ---------- |
| **Strategy A: 고정 예산**  | 웹 본문에 최대 4,500 토큰 할당 (3페이지 × 1,500 토큰)      | ⭐⭐⭐⭐   |
| **Strategy B: 동적 예산**  | RAG 결과가 풍부하면 웹 본문 축소, 부족하면 확대            | ⭐⭐⭐⭐⭐ |
| **Strategy C: 2단계 요약** | 크롤링 본문을 LLM으로 먼저 요약(500토큰) → 메인 LLM에 전달 | ⭐⭐⭐     |

#### 3-4. 추천: Strategy B (동적 예산 분배)

```typescript
function calculateWebTokenBudget(ragResultCount: number): number {
  if (ragResultCount >= 5) return 1500; // RAG 충분 → 웹 보충만
  if (ragResultCount >= 2) return 3000; // RAG 보통 → 웹 중간
  return 4500; // RAG 부족 → 웹 최대
}
```

> **이유**: PrismLM의 핵심 가치는 "사용자 문서 기반 평가"입니다.
> RAG 결과가 풍부할 때 웹 본문이 프롬프트를 지배하면 안 됩니다.
> 동적 분배로 RAG 우선 원칙을 유지하면서 웹 정보를 보충하는 것이 최적입니다.

#### 3-5. Jemiel Strategy 통합

> 웹 본문 요약에 사용할 LLM 컨텍스트를 `llm-usage-map.ts`에 추가해야 합니다.


### 안건 4: 비용·속도 트레이드오프 — 캐싱, 선택적 크롤링, 비동기 처리

**발언자: 최예린 (비용 & 지연시간 최적화 전문가)**

> 안녕하세요, 최예린입니다. LLM 서비스의 운영 비용과 사용자 체감 속도 최적화를 전문으로 합니다.

#### 4-1. 비용 분석 (크롤링 추가 시)

```
AS-IS (스니펫만):
├── Brave Search API: 1회 호출          = 무료 (2,000/월)
├── LLM 입력 토큰: ~4,800 토큰          = $0.0024
├── LLM 출력 토큰: ~2,700 토큰          = $0.0081
└── 총 비용/요청: ~$0.0105

TO-BE (Deep Reading 추가):
├── Brave Search API: 1회 호출          = 무료
├── Jina Reader API: 3회 호출           = 무료 (일일 제한 내)
├── LLM 요약 (gemma-3-4b): ~4,500 토큰  = $0.0009
├── LLM 입력 토큰: ~8,800 토큰          = $0.0044
├── LLM 출력 토큰: ~2,700 토큰          = $0.0081
└── 총 비용/요청: ~$0.0134

비용 증가: +$0.0029/요청 (+28%)
월간 (300회 기준): +$0.87/월
```

> **결론: 비용 증가는 미미합니다.** 월 $1 미만 추가로 정보 품질이 크게 향상되므로 ROI가 매우 높습니다.

#### 4-2. 지연시간 분석

```
AS-IS 타임라인:
0ms ──── 검색 API (500ms) ──── LLM 스트리밍 시작 (TTFT 1.5s) ────→
         ↑ 병렬: RAG 검색

TO-BE 타임라인 (순차 방식 — 비추천):
0ms ── 검색 API (500ms) ── 크롤링 3페이지 (3s) ── LLM 시작 (TTFT 5s) ──→
                                                    ↑ 사용자 5초 대기 ❌

TO-BE 타임라인 (병렬 + Progressive — 추천):
0ms ── 검색 API ─────────────────── LLM 스트리밍 시작 (TTFT 1.5s) ──→
       ↑ 병렬: RAG 검색              ↑ RAG 결과로 먼저 응답 시작
       ↑ 병렬: 크롤링 3페이지 ──────── 크롤링 완료 시 보강 정보 추가 ──→
```

#### 4-3. 추천: 2-Phase 응답 전략

> 핵심 아이디어: **RAG 결과로 먼저 응답을 시작**하고, 크롤링이 완료되면 **웹 본문을 보강 정보로 추가**합니다.

```
Phase 1 (즉시 응답):
├── RAG 검색 결과 + 웹 스니펫으로 LLM 응답 시작
├── 사용자 체감 TTFT: 기존과 동일 (1.5초)
└── 상태 메시지: "📚 답변 생성 중..."

Phase 2 (보강 정보):
├── 크롤링 완료 후 핵심 정보 요약
├── 응답 하단에 "🌐 웹 심층 정보" 블록 추가
└── 상태 메시지: "🔍 웹 페이지 분석 완료"
```

> **그러나 구현 복잡도를 고려하면**, 현실적으로는 **크롤링을 검색과 함께 병렬로 실행**하고,
> 전체가 완료된 후 LLM에 한꺼번에 전달하는 방식이 1차 구현으로 적합합니다.

#### 4-4. 선택적 크롤링 전략

> 모든 검색 결과를 크롤링하면 비용과 시간이 낭비됩니다. **상위 N개만 선택적으로 크롤링**해야 합니다.

| 전략            | 크롤링 대상                             | 예상 시간   | 추천              |
| --------------- | --------------------------------------- | ----------- | ----------------- |
| **Top 1**       | 가장 관련도 높은 1개                    | ~1초        | 보수적, 빠름      |
| **Top 3**       | 상위 3개 병렬                           | ~2초 (병렬) | ⭐ 균형           |
| **Top 5**       | 상위 5개 병렬                           | ~3초 (병렬) | 정보량 최대, 느림 |
| **신뢰도 기반** | trustBadge가 academic/government인 것만 | ~1~2초      | 품질 우선         |

**추천: Top 3 병렬 크롤링** + 페이지당 5초 타임아웃 + 실패 시 스니펫 폴백

#### 4-5. 캐싱 전략

### 안건 5: 크롤링 본문의 신뢰도 검증 — 기존 Self-RAG 파이프라인 통합

**발언자: 김태윤 (신뢰도 검증 & 팩트체킹 전문가)**

#### 5-1. 웹 크롤링 본문의 신뢰 위험 분석

> 스니펫만 쓸 때보다 본문을 직접 읽으면, **정보량이 증가하지만 동시에 위험도 증가**합니다.

| 위험 요인                   | 설명                                                                                 | 심각도  |
| --------------------------- | ------------------------------------------------------------------------------------ | ------- |
| **잘못된 정보의 깊은 인용** | 스니펫은 피상적이라 피해 제한적이었으나, 본문 인용은 "근거 있는 오류"를 만들 수 있음 | 🔴 높음 |
| **광고성 콘텐츠 혼입**      | 블로그 본문에 섞인 마케팅 문구를 사실로 인용                                         | 🟡 중간 |
| **시점 불일치**             | 크롤링된 정보의 작성 시점과 현재 시점의 괴리                                         | 🟡 중간 |
| **저작권 과다 인용**        | 원문 대량 인용 시 저작권 이슈                                                        | 🟡 중간 |

#### 5-2. 기존 Self-RAG 파이프라인 확장 방안

> PrismLM의 Self-RAG는 4단계 검증을 수행합니다. 웹 크롤링 본문도 이 파이프라인에 통합할 수 있습니다.

```
기존 Self-RAG 파이프라인:
Step 1: checkRetrievalNecessity()    → 검색 필요 여부
Step 2: critiqueRetrievalResults()   → 검색 결과 관련도
Step 3: verifyGroundedness()         → 답변 근거 검증
Step 4: (암묵적) LLM 생성

Deep Reading 확장:
Step 1: checkRetrievalNecessity()    → 동일
Step 2: critiqueRetrievalResults()   → RAG + 웹 본문 통합 평가
Step 2.5: ★ verifyWebSource()       → 웹 본문 신뢰도 사전 검증 (NEW)
Step 3: verifyGroundedness()         → RAG + 웹 본문 교차 검증
Step 4: LLM 생성
```

| 1   | **RAG 우선**             | 사용자 문서가 항상 최우선, 웹 본문은 보충 역할    |

| 3   | **선택적 크롤링**        | 모든 URL이 아닌 상위 3개만 크롤링 (비용·속도)     |
| 4   | **본문 미저장**          | 원문은 저장하지 않고 요약본만 캐시 (저작권)       |
| 5   | **Feature Flag 롤백**    | `ENABLE_DEEP_READING=false`로 즉시 기존 동작 복원 |
| 6   | **보안 우선 크롤링**     | SSRF, private IP, redirect, content-type, 응답 크기 제한을 기본 적용 |
| 7   | **개인정보 최소 전송**   | 사용자 문서는 외부 검색/크롤링 공급자에 전송하지 않고, 검색 질의는 PII 마스킹 후 사용 |
| 8   | **측정 가능한 롤아웃**   | Shadow Mode와 운영 지표 기반으로 단계 배포 및 즉시 롤백 |

> 기존 RAG 로그 및 Shadow Mode 로깅 패턴을 재활용하여 fire-and-forget 방식으로 수집합니다.

| 지표                  | 목표/임계치                            | 초과 시 대응                                      |
| --------------------- | -------------------------------------- | ------------------------------------------------- |
| `crawl_success_rate`  | 목표 80% 이상, 10분 평균 70% 미만 경보 | `ENABLE_DEEP_READING=false` 또는 Top 3 → Top 1 축소 |
| `fallback_rate`       | 목표 30% 이하, 10분 평균 40% 초과 경보 | Jina/Readability 장애 점검, 일시적 스니펫 모드 전환 |

| `citation_pass_rate`  | 목표 85% 이상                          | 웹 컨텍스트 가중치 하향, Shadow Mode 재검증       |
| `cost_per_request`    | 목표 $0.02 이하                        | Top N 축소, 요약 토큰 제한 강화                   |
| `cache_hit_rate`      | 웜업 후 25% 이상                       | TTL/도메인 정책 조정                              |

### 9.1 추가 초빙 전문가 의견

실제 프로덕션 레벨 검토를 위해 아래 5명의 전문가 관점을 추가로 반영하였습니다.

| 전문가 | 추가해야 하는 내용 | 이유 |
| ------ | ------------------ | ---- |
| **이수민** — AppSec 전문가 | SSRF 방어, private IP 차단, redirect 제한, content-type/응답 크기 상한, 프롬프트 인젝션 필터링 | 크롤러는 네트워크/프롬프트 양쪽에서 공격면이 넓어 보안 가드가 선행되어야 함 |
| **오민재** — SRE/관측성 전문가 | `crawl_success_rate`, `fallback_rate`, `p95_latency_ms`, `citation_pass_rate`, `cost_per_request` 지표와 자동 롤백 기준 | 목표 수치만 있고 운영 중 이상 징후를 감지하는 체계가 없으면 품질 회귀를 늦게 발견함 |
| **정하린** — LLM Evals 전문가 | 평가셋 구축, Shadow Mode 비교, AS-IS vs TO-BE 정량 검증 | 딥 리딩은 더 깊은 답변을 만들지만, 틀릴 때 더 그럴듯하게 틀릴 수 있어 사전 평가가 필수 |
| **서민규** — 프라이버시/컴플라이언스 전문가 | 외부 전송 경계 정의, 검색 질의 PII 마스킹, Enterprise opt-out, 캐시 삭제 정책 | 저작권 외에도 사용자 데이터가 어디까지 외부로 나가는지 명확히 정의해야 운영 승인 가능 |
| **배도현** — 검색 품질/랭킹 전문가 | 도메인 다양성, 1차 출처 우선, 최신성 가중치, UGC/복제 기사 다운랭크 | 어떤 페이지를 읽느냐가 본문 추출 품질만큼 중요하며 동일 기사 3개는 정보 증가 폭이 제한적임 |

### 9.2 기술 리더 종합 보완 제안

실제 프로덕션 레벨 적용을 위해 다음 5가지 핵심 사항의 보완을 제안합니다.

1. **보안 및 프롬프트 인젝션 방어 (Security & Sanitization)**: 크롤링 본문을 통한 간접 프롬프트 인젝션(Indirect Prompt Injection)을 방어하기 위해 `contentExtractor.ts` (Phase 2)에 탐지 및 필터링 로직 추가 필요.
2. **크롤링 병렬 처리 시 부분 실패 용인 (Graceful Partial Degradation)**: 외부 API 타임아웃 등 에러 발생 시 전체가 실패하지 않도록 `Promise.allSettled()`를 활용한 부분 성공 허용 로직 처리.
3. **도메인/시의성 기반 동적 캐싱 전략 (Dynamic Cache TTL)**: 일괄 24시간 캐싱 대신, 정보의 휘발성(뉴스 vs 학술 자료)에 맞춘 스마트한 동적 캐싱 정책 도입 필요.
4. **서브 LLM 호스팅 인프라 명시**: 500ms 지연시간 목표 달성을 위해 `gemma-3-4b-it` 모델을 구동할 구체적인 인프라(예: Groq, 외부 API 등) 및 통합 방안 명시 필요.
5. **UI/UX: 인용 출처의 시각적 분리 (Transparency in UI)**: 생성된 답변의 `[웹1]` 마커 인터랙션 시 도메인명, 타이틀, 파비콘 등 출처 정보를 내부 RAG 문서와 시각적으로 명확히 구분하여 노출하는 설계 필요.

> 위 추가 전문가 의견과 보완 제안은 본 문서의 <4. 합의 사항>, <5. 구현 단계 계획>, <6. 리스크 및 대응>, <7. 향후 확장 가능성>에 반영하였습니다. 현재 문서는 아이디어 수준을 넘어, 점진 배포와 운영 검증까지 고려한 프로덕션 설계 문서에 가깝습니다.
